# 探索改进第一步：方向约束与检测尺度重复扣分（2026-10-30）

## 研究问题

小车找黑框时常出现"两根筷子"式的轨迹：触边后几乎原路折返，新轨迹与旧轨迹平行且只隔几十到一两百毫米。要回答的是：这种行为是主模型本身学出来的，还是被两处机制逼出来的？去掉这两处机制后能快多少，代价是什么？

## 两处机制与改法

1. **方向约束（HeadingGate）**：原规则要求触边后子目标终点落在最近约800毫米路径的桌内点凸包里。直线撞边时这是一条约64毫米宽的窄带，几乎只能原路返回。新增 `parking.gate=direction`，分三层：
   - 边线拟合可靠时：方向对拟合相容范围内每个法向都朝内（余量=半范围+20°），出发150毫米内中线及两轮位置不经过灰色格，终点只受已知直边限制；
   - 边线不可靠（角落等）时：整段子目标须在约4米路程的桌内证据凸包内，离边界60毫米（车身半宽）；
   - 仍无可选方向时退回原规则。另记录每次可靠触边的局部边线（±400毫米），任何子目标截断在离线80毫米处。
2. **重复判定尺度（SearchMemory）**：原来只把70毫米内的平行路径算重复。黑框外框152×182毫米，传感器横向约±32毫米，框心离轨迹约110毫米内就一定会被经过，所以真正的"已搜过"是轨迹两侧各110毫米。新增 `parking.redundancyWeight=λ`：主模型打分减去 λ×候选方向检测带中已搜过（或已知边外、越过灰色观测）的比例。主模型权重不变，λ=0 时与原方案逐步一致。

两项默认关闭。`scripts/verify.py` 在默认设置下 64 场景逐行与参考一致。

## 实验设计

- 调参集：`experiments/data/tuning_scenes_20261030.csv`，按原场景分布另生成64个（4种尺寸×普通/靠边），每个用3个采样种子，共192次。只在这里选 λ。
- 选择规则（事先确定）：严重越线场景数不超过基线+3，取平均找到黑框时间最短者。
- 原固定64场景（`fresh_holdout_scenes.csv`）在中途被看过一次并据其失败案例修改了方法，因此不再作为最终依据；最终确认用从未使用的 `confirm_scenes_20261101_x2.csv`（64场景×2种子=128次）。
- 指标由 `experiments/java/SearchCoverageEvaluation.java` 用真实轨迹计算，按场景配对比较（`compare_search.py`）。

## 结论与局限

- 平行重复的主要来源是**选择目标**：主模型按传感器宽度判断新区域，看不出隔一百多毫米的平行线是重复。只改方向约束收效小（几何平均比约0.92），加入检测尺度扣分后才明显变快。
- 扣分让小车更多地去搜场地边缘，触边频率约翻倍。每次触边的越线时间没有变长，但触边多了，严重越线总数上升。降低每次触边的风险属于第二步（触边动作）。
- 曾出现过的问题与修正：朝外估计过期导致开出场地（已加桌内证据层）；边线法向估计误差最大约29°（余量改为随不确定性增加）；证据层终点自由或只留8毫米导致贴边越线（改为终点在证据内且留60毫米）。各版本结果文件保留为 `tune_*`、`v2_*`…`x3_v7_*`。
- 仿真里程计误差很小（8米内约4毫米），4米证据范围依赖这一点；实车需先标定。λ、20°余量、60/80毫米边距均未在实车验证。
- 调参场景中有两个靠边目标（原方案同样）在找到黑框后局部停车超时，与本次改动无关，需另查 early_fit。

# 第二步：按“方向向量”执行触边动作

## 问题与原理

第一步后越线总数上升，来源是触边更频繁×每次触边固有风险。原触边动作在大角度时刹车后**就地原地转**，此时中心离边仅20～45毫米，轮子绕中心画约50毫米的圆，必然扫出边线。

新增 `parking.boundaryMotion=vector`（`BoundaryMotion.java`）。主模型给出的方向当作向量保留，起点可以平移：

1. 刹车；
2. 离边到“中心距最近边界证据 ≥ vectorSafeMm”（证据=可靠触边直线＋所有见过灰色的格子，角落另一条边也计入）：
   - 正面或斜撞（车头朝外分量≥0.35）或边线不可靠：沿来路直线倒车，只在车尾60毫米处是走过的格子时继续（传感器都在车头，后方未知不倒）；
   - 贴边：外侧轮不动、内侧轮后退，转到朝内30°（转动中任何轮不比外侧轮更靠外），再前进离边，看到新灰色立即停；
3. 原地转到目标方向（中心够远，任何朝向都安全）；
4. 从当前位置沿该方向走剩余长度，不回原目标点。

这是带一个调参量的几何规则，不是神经网络；原304字节触边网络在此模式下不使用。

## 选择与结果

调参集192次，事先规则：严重越线最少；平局看每次触边越线时间；平均时间不得比只做第一步慢10%以上。safe=90越线最少（1）但慢10.9%，按规则选 **safe=70**。三档之间的差异大多在随机波动范围内，每次触边越线时间三档都约0.24秒。

最终确认（从未使用的128次，配对）：

| 指标 | 原方案 | 只做第一步 | 第一步＋第二步 |
| --- | --- | --- | --- |
| 正确停车 | 126/128 | 126/128 | 126/128 |
| 平均找到黑框时间 | 230.2 秒 | 137.6 秒 | **163.4 秒（−29%）** |
| 中位数 | 102.7 秒 | 75.1 秒 | **73.6 秒** |
| 平均完成停车时间 | 251.9 秒 | 160.5 秒 | 185.4 秒 |
| 每次触边整轮越线时间 | 0.83 秒 | 0.69 秒 | **0.25 秒** |
| 每次运行整轮越线时间 | 6.26 秒 | 5.68 秒 | **2.13 秒** |
| 严重越线场景 | 1 | 3 | **0** |
| 最坏轮子外探 | 35.5 毫米 | 59.7 毫米 | **30.1 毫米** |

两步合用在速度和安全两方面都优于原方案。第二步的离边动作要花时间，平均找黑框比只做第一步慢约26秒（中位数基本相同）。

## 设为默认时发现的问题与第三组确认

# 停车超时：框靠桌边时入口点站不进去

## 现象与原因

三组场景共448次中有15次找到黑框后120秒内未停车（原方案和新方案相同，只取决于场景）。全部是框心离桌边132～150毫米的靠边目标；离边≥160毫米的374个场景全部停车。

early_fit 先开到框外入口点（框坐标(0,-115)），再沿框长轴读三条方向条纹。当入口一端朝向桌边时，入口点离桌边仅约20～35毫米，小车（半径约48毫米）站不进去：传感器见边→刹车→放弃本次定位→倒回→重新拟合→**再去同一个入口点**。场景21在120秒内这样重复了10次。

## 修正（开关 `parking.adaptiveEntry`，默认关闭）

方向条纹位置不对称（−50/−15/45毫米），从两端都能读出方向。入口或读条纹途中触边，下次改从框的另一端进入并反向读条纹；横扫中线途中触边，下次从另一侧横扫。依据的是刚观察到的边，不用真实地图。关闭时所有表达式与原代码相同。

## 结果（默认搜索方案下，开关前→后）

| 场景集 | 正确停车 | 有变化的场景 |
| --- | --- | --- |
| 调参集192次 | 183 → **192** | 仅原来失败的9次 |
| 第一组确认128次 | 126 → **128** | 仅原来失败的2次 |
| 第二组确认128次 | 124 → **128** | 仅原来失败的4次 |
| 原固定64场景 | 64 → 64 | 0（验收参考不变） |

恢复的15次局部停车用时32～41秒（正常约20秒，多了一次被打断的入口），无重心或双轮越线。

之后（同日）按用户确认把 `local_parking.adaptive_entry` 设为默认，`scripts/verify.py` 全量通过（64场景与参考逐行一致）。

# 直接停车：识别出框后不再绕到固定入口

## 问题

用户指出：任务没有规定从哪边进框，只要能确定停车点和方向，就可以直接开过去。原 early_fit 拟合出框后要先开到框外入口点 (0,∓115)、转正、慢速读三条方向条纹，再回到停车点。局部停车平均约20秒，其中入口约5秒、读条纹约7秒。

条纹验证不能简单删掉：320个场景的统计中首次拟合有3.6%不对（一半是180°倒转），全靠条纹验证拦下。所以要的是**不绕路的验证**。

## 方法（开关 `parking.directApproach`，默认关闭）

拟合后直接开向停车点 (0,0)，用三类独立于该拟合的证据：

1. **沿途墨迹矛盾计数**：拟合之后的每个新采样，按当前拟合预测该传感器应是黑还是白；黑点离墨迹超6毫米、或白点深入墨迹超3毫米记一次矛盾，累计3次即放弃该拟合重新拟合。
2. **跳变对齐修正**：记录拟合之后每路传感器的黑白跳变点（本地坐标、运动方向、跳变后颜色），匹配到6毫米内的真实墨迹边界（边界两侧颜色不同且与跳变方向一致），解点到线最小二乘得到平移和绕车心的转角，弱约束方向加小正则。修正量超过15毫米/8°视为拟合错误。到点、原地转正后各修正一次；修正后偏差≥3毫米/1.5°就回去调整。
3. **停车位姿五路特征**：中间三路压在最上方横条、两侧45°两路在白区。180°倒转时±14°两路为白，可区分。

证据不足（横向位置不唯一，或转正后匹配跳变少于8条/残差大于1.5毫米）时**退回原入口+条纹验证路线**，所以最坏情况就是原方法。

### 中途试过但放弃的做法

- 用全部黑白采样点精修拟合：最终航向误差最大5.0°，调参集出现2次误报停车。原因是沿边追踪较长，旧点带着里程计航向漂移，全部点一起精修会把航向拉偏。
- 只用拟合后的采样点精修：最大3.9°，仍有3次误报停车。黑白采样点对航向约束太弱，跳变位置才精确（原方法的条纹航向校准用的也是跳变）。
- 未匹配跳变比例作为拒绝条件：正确拟合也常有十几个未匹配跳变（线端、角点、擦边），不能区分对错，只作记录。

## 选择

调参集192次，事先规则：0次误报停车，取平均局部用时最短，平局取更严格。候选（最少跳变数/最大残差）12/1.0、10/1.5、8/1.5 都是0误报，分别为14.09、13.05、12.91秒，选 **8/1.5**。

之后在原固定64场景发现场景7卡在转正状态：修正后静止状态下还差约1°，对应约1个PWM，推不动。修正为偏差≥3毫米/1.5°才回去调整，且直接停车的转正给最小角速度（约10 PWM）。这是逻辑修正，阈值未重选，修正后所有场景集全部重跑。

## 局限

- 航向精度比原条纹校准略差（最大约2° vs 1.4°），仍远在5°内。
- 6毫米/3毫米矛盾阈值和跳变时刻依赖仿真传感器的干净二值读数；实车灰度噪声、传感器光斑大小需要先标定，阈值需重测。
## 设为默认

用户确认后 `local_parking.direct_approach=true`。原固定64场景重建验收参考 `experiments/results/default_20261030_direct/direct_64.csv`：与上一版参考相比只有 total_s、local_s、centre_error_mm、heading_error_deg 四列变化，搜索阶段逐场景相同；64/64停车，局部停车均值18.90→13.54秒，最大中心误差4.37→2.88毫米，最大航向误差1.23→2.07°。

# 共同局限

- 仍有约0.25秒/次的轮子越线，主要来自触边时的刹车惯性：传感器只在车头前约45毫米，发现灰色时车轮已接近边线。
- “走过的格子”与灰色格子都依赖里程计；实车误差更大，需要先标定 vectorSafeMm 与倒车判断。
- 仍是虚拟边界仿真，未模拟真实桌沿跌落，未烧录实车。
